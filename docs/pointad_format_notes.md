## Dataset root and discovery

PointAD does NOT use any env var or config file. The dataset root is passed via CLI:

- `train.py --train_data_path <DATASET_ROOT>`
- `test.py  --data_path       <DATASET_ROOT>`

Inside the dataset root, `dataset.Dataset.__init__` reads a JSON manifest:

- In `is_all=True` mode (test): loads `<DATASET_ROOT>/all_meta.json`.
- In single-class mode (train): loads `<DATASET_ROOT>/<train_dataset_name>_meta.json`.

The manifest file lives **inside the dataset root directory itself** (not in a separate `manifests/` folder). All path fields inside the JSON are stored as `<DATASET_ROOT>/...` strings — they are joined back to absolute on disk via `self.root` (so they're effectively root-relative when written by the generators, but become absolute once the root is fixed).

The "renderings" the model actually consumes are NOT the raw RGB / XYZ files — they are pre-generated multi-view 2D images + 2D ground-truth + 2D-3D correspondence files produced by `multi_view/multiview_*.py`. PointAD is therefore a **two-stage offline-rendering pipeline**, not a directly-from-RGB-and-XYZ model.

## Manifest format (if used)

**Yes, PointAD uses a manifest file.** It is JSON, written by the scripts in `generate_dataset_json/`. The schema is dataset-shape-dependent (MVTec/Eyecandies vs Real3D), and is NOT the simple `{train: [...], test: [...]}` schema the Phase 1 plan currently sketches.

Top-level shape (in `<DATASET_ROOT>/all_meta.json`):

```json
{
  "train": {
    "bagel":  [<sample>, ...],
    "cable_gland": [...],
    ...
  },
  "test":  {
    "bagel":  [<sample>, ...],
    ...
  }
}
```

i.e. the outer dict is keyed `{train, test}` and the inner dict is keyed by **class name**, with sample lists per class. Note `mvtec_3d_anomaly_mvtect_3d_ad_whole.py` only emits the `test` half — `train` stays empty `{}`. The class-specific `<cls>_meta.json` files are emitted by the `*_class_specific.py` variants for training.

Per-sample schema — **MVTec3D-AD** (`mvtec_pc_3d_rgb`):

```json
{
  "d2_img_path":         "<root>/bagel/test/combined/rgb/000.png",
  "d2_mask_path":        "<root>/bagel/test/combined/gt/000.png",
  "d3_pc":               "<root>/bagel/test/combined/xyz/000.tiff",
  "cls_name":            "bagel",
  "specie_name":         "combined",
  "anomaly":             1,
  "d2_render_img_path":  "<root>/bagel/test/combined/2d_rendering/000",
  "d2_render_gt_path":   "<root>/bagel/test/combined/2d_gt/000",
  "d2_corrdinate":       "<root>/bagel/test/combined/2d_3d_cor/000"
}
```

Per-sample schema — **Eyecandies** (`eye_pc_3d_rgb`): same as MVTec3D-AD plus one extra `d3_pcd_path` field pointing to `gt_pcd/<id>.pcd`. Geometry source is `pcd/` not `xyz/`.

Per-sample schema — **Real3D-AD** (`real_pc_3d_rgb`): same shape minus `d2_img_path` (no RGB), and `d2_mask_path` points to `gt_pcd/<id>.pcd` (a colored PCD whose vertex colors encode the per-point anomaly label, not a 2D PNG mask).

Note (typo preserved from upstream): the field is spelled `d2_corrdinate` (missing the second "o"), not `d2_coordinate`. Adapters MUST emit the misspelled key or `Dataset.__getitem__` will KeyError.

**This is a major surprise vs the Phase 1 plan.** The plan's assumed schema `{"id", "rgb": [...], "pcd", "gt_mask", "class", "anomaly"}` is fictional; PointAD's actual manifest is keyed differently AND requires *pre-rendered* `2d_rendering` / `2d_gt` / `2d_3d_cor` directories on disk. Phase 1 Tasks 5–11 (manifest + adapters) need to be reformulated:

1. The adapters must also produce per-sample multi-view 2D renderings (via `multi_view/multiview_*.py` or a re-implementation), 2D ground-truth masks, and 2D-3D correspondence .npy files — not just point cloud + RGB.
2. The manifest schema must match the keys above (`d2_img_path`, `d3_pc`, `d2_render_img_path`, `d2_render_gt_path`, `d2_corrdinate`, `cls_name`, `specie_name`, `anomaly`).
3. The top-level structure is `{train: {cls: [...]}, test: {cls: [...]}}`, not `{train: [...], test: [...]}`.

## Train.sh entrypoint

`bash train.sh` (no args). It is a static shell script that hard-codes three sweeps in sequence:

1. **MVTec3D-AD**, classes `cookie`, `carrot`, `dowel` (one-vs-rest training, 3 classes only). Calls `python train.py` then `python test.py`.
2. **Eyecandies**, classes `PeppermintCandy`, `LicoriceSandwich`, `Confetto`. Same pattern.
3. **Real3D-AD**, class `seahorse` only (the other two `shell`, `starfish` are commented out). Calls `python test_only_point.py` (not `test.py`).

`train.py` CLI flags (from `train.py`):

```
--train_data_path    str  e.g. /remote-home/iot_zhouqihang/data/mvtec_3d_mv/mvtec_3d_9_views
--save_path          str  checkpoint output dir, e.g. ./exps_9_12_4_mv9_mvtec_3d_336_4/cookie/
--dataset            str  one of {mvtec_pc_3d_rgb, eye_pc_3d_rgb, real_pc_3d_rgb}
--train_dataset_name str  the single class to train on (used to load <cls>_meta.json)
--depth              int  prompt-tuning depth, default 9
--n_ctx              int  prompt context length, default 12
--t_n_ctx            int  text prompt context length, default 4
--feature_map_layer  int+ default [0,1,2,3]
--features_list      int+ which CLIP layer features to extract, e.g. [24] for MVTec/Eye, [6,12,18,24] for Real3D
--epoch              int  default 15
--learning_rate      float default 1e-3
--batch_size         int  default 8 (train.sh uses 4)
--image_size         int  default 518 (train.sh uses 336)
--point_size         int  default 336
--print_freq, --save_freq, --seed
```

Hard-coded paths (`/remote-home/iot_zhouqihang/data/...`) must be substituted before the script is runnable on our Windows workstation.

## Test.sh entrypoint

`bash test.sh` (no args). Same three-loop structure as `train.sh`, just without the training step. Loads the checkpoint `${save_dir}epoch_15.pth` and runs `test.py` (MVTec/Eye) or `test_only_point.py` (Real3D).

`test.py` CLI flags:

```
--data_path        str  dataset root
--save_path        str  results dir
--checkpoint_path  str  e.g. ./exps_.../cookie/epoch_15.pth
--dataset          str  {mvtec_pc_3d_rgb, eye_pc_3d_rgb, real_pc_3d_rgb}
--features_list    int+ default [6,12,18,24]
--image_size       int  default 518 (test.sh uses 336)
--depth, --n_ctx, --t_n_ctx, --feature_map_layer  prompt-tuning hyperparams
--metrics          str  {image-level, pixel-level, image-pixel-level}, default image-pixel-level
--sigma            int  Gaussian filter sigma for anomaly-map post-processing, default 4
--train_class      str  the auxiliary class this checkpoint was trained on (excluded from eval)
--point_size       int  default 336
--seed             int  default 111
```

`test_cross_dataset.sh` is a separate variant: trains on MVTec3D-AD, tests on Eyecandies / Real3D-AD (the zero-shot cross-dataset protocol our welds zero-shot Task 15 mirrors).

## CLIP checkpoint expectations

PointAD uses `ViT-L/14@336px`, loaded by `AnomalyCLIP_lib/model_load.py:load()`.

- Auto-downloads from OpenAI's public S3:
  `https://openaipublic.azureedge.net/clip/models/3035c92b350959924f9f00213499208652fc7ea050643e8b385c2dac08641f02/ViT-L-14-336px.pt`
- **Cache directory is hard-coded** to `/remote-home/iot_zhouqihang/root/.cache/clip` (the original author's machine!) at `model_load.py:38, 145`. On Windows this expands to `C:\remote-home\iot_zhouqihang\root\.cache\clip` which the script will create — annoying but not fatal. **Workaround for our setup:** pass `download_root="<our cache>"` from outside, OR symlink/redirect; since we cannot modify `external/PointAD/`, we will need to either let it create the spurious `C:\remote-home\...` path or wrap `model_load._download` via a shim in our own runner.
- No local-checkpoint mode is wired into `train.sh` / `test.sh`. If the auto-download is blocked by network, the user can pre-place the `.pt` at the hard-coded path.

In addition, PointAD ships its own learned **prompt-learner checkpoints** at `external/PointAD/exps_9_12_4_mv9_mvtec_3d_336_4/{cookie,carrot,dowel}/epoch_*.pth` (and equivalents for `..._eye_3d_336_4/` and `..._real_3d_336_4/`). These are what `test.sh` consumes. We can skip the training step for baseline reproduction by pointing `--checkpoint_path` at these shipped weights.

  And the corresponding pixel branch at lines 148–149 (`color_similarity_map = similarity_map[-b:]`).

- The fusion of point-branch and color-branch scores happens at lines 167–168 (`integrate_anomaly_map = (color_anomaly_map + anomaly_map)/2`) and 171–173 (`integrate_pr_sp`).

**For Phase 2, this is the surgical patch site.** Replace the single `image` tensor (which is `items['img']`, one RGB image per sample) with our M-photo / Phong stack, change the `[-b:]` slice to `[-M*b:]`, and substitute the simple `(color + point) / 2` fusion at line 167 with our learned fusion module.

`test_only_point.py` is the RGB-free variant (used for Real3D-AD); it would NOT be the patch site.

## Install gaps

`pip install`s needed on this Windows + Python 3.13 + PyTorch 2.6 + CUDA 12.4 environment beyond what is already present:

1. **`open3d` — NOT installable on Python 3.13.** Latest open3d wheel is for Python ≤3.12. The `dataset.py:101` import (`import open3d`) AND `multi_view/*.py` imports of `open3d as o3d` will both fail. **Action needed:** either (a) create a separate Python 3.12 venv just for PointAD, or (b) monkey-patch / replace open3d usage in our own runner (only `open3d.io.read_point_cloud` is touched inside `Dataset.__getitem__`, used for Real3D-AD ground-truth color-PCD parsing; this could be swapped for a plain ASCII-PCD parser).

2. **`pkg_resources.packaging` import is broken** in setuptools ≥ 71 (we have 70.2.0 but the symbol is already removed, so the upgrade window was tighter than expected). Affects both `AnomalyCLIP_lib/model_load.py:6` and `prompt_ensemble.py:3`. **Action needed:** either (a) install `pip install --user 'setuptools<70.2'` (rolls back to a version that still exposes `pkg_resources.packaging`), or (b) shim `pkg_resources.packaging = packaging` before importing PointAD modules. The plan forbids editing `external/PointAD/` so option (b) goes in our wrapper.

3. **`ipdb`** — imported unconditionally at `multi_view/multiview_mvtec.py:11` (and likely other multi_view scripts). Only matters if we rebuild renderings; for using shipped renderings it doesn't. `pip install ipdb` if needed.

4. Standard scientific stack (`scipy`, `scikit-image`, `scikit-learn`, `tabulate`, `tifffile`, `PIL`, `tqdm`, `seaborn`, `timm`, `torchsummary`, `dash-table`, `cv2`) — most are already in the env; install as needed when the actual import fires.

5. **Hard-coded Linux paths** at `model_load.py:38, 145` (`/remote-home/iot_zhouqihang/root/.cache/clip`) are not technically an install gap but will silently create `C:\remote-home\iot_zhouqihang\root\.cache\clip` on first run. Pre-place the CLIP checkpoint there or shim `AnomalyCLIP_lib.model_load._download` from our wrapper.

**Bottom line:** import-clean operation requires fixing items 1 and 2 first. Recommended sequence: (1) create a Python 3.12 venv with pinned `setuptools==69.5.1`, install open3d there, and use that venv as the PointAD subprocess interpreter; OR (2) write a thin wrapper that monkey-patches the two import issues before importing PointAD and refactors the one open3d call site.
